# 작업 진행·마감·보고 규칙

## 시작 순서
1. 기존 파일과 환경을 확인하고 관련 규칙을 읽는다. 사용자 파일을 덮어쓰지 않는다.
2. 현재 시각과 마감 잔여시간을 확인한다. `STATUS.md`에 작업 계획, 팀 역할, 실행 가능 기능, 미정 사항, 가정을 기록한다.
3. 지원되면 역할별 에이전트를 구성한다. 전략팀은 개별 디렉터리에서 작업한다. 불가능하면 순차 역할 수행을 기록한다.
4. 조사와 공통 엔진 구축을 시작한다. 가능한 가장 단순한 전략으로 데이터→주문→체결→원장→보고서 전체 경로를 먼저 검증한다.
5. 공통 평가 기준을 동결하고 전략 후보를 개발한다. 모의거래는 검증된 후보부터 일찍 시작한다.

늦게 시작하면 구현 범위를 줄여 보고서 마감을 우선한다. 관측하지 않은 기간을 채워 넣지 않는다.

## 지속 실행
세션 종료 이후 자동으로 연구가 이어진다고 약속하지 않는다. 장시간 데이터 수집은 로그·PID·체크포인트·중단 및 복구 명령을 갖춘 로컬 프로세스로 실행한다. 예약 기능이 있으면 지원 범위 안에서 실행 예약을 준비한다. 예약이 없으면 사용자가 언제 무엇을 다시 실행해야 하는지 적는다. OS 예약 작업은 검증된 스크립트만 실행하도록 구성하고 기존 작업을 변경하지 않는다. 프로세스가 실제 실행 중인지와 마감 파일 생성이 가능한지 확인한다.

## 진행 관리
단계 종료마다 STATUS.md와 실험 레지스트리를 갱신한다. 차단 요인, 실패, 새로운 가정, 실행 명령을 남긴다. 컨텍스트가 줄어들면 HANDOFF.md에 현재 상태와 다음 행동을 저장한다. 같은 실험을 중복 실행하지 않는다. 외부 유료 API·리소스 사용은 별도 승인이 필요하다.

## 최종 보고서 목차
1. 결론: 채택/보류/폐기, 검증 수준과 이유.
2. 검증된 대회 우승자 목록과 근거, 부문 차이.
3. 공개 전략 및 공통/상충 원칙, 미공개 항목.
4. 개발한 전략의 정량 규칙과 원문 대비 추가 가정.
5. 데이터·상품·비용·체결·통신·위험 모형.
6. 공통 조건 경합표와 과거/실시간/testnet 결과 구분.
7. 실패 전략, 과최적화 점검, 비용/지연 민감도.
8. 관측 기간·거래 수·미구현 요소·현실과 차이.
9. 다음 검증 계획과 실거래 전 충족할 조건.
10. 재현 명령, 코드 버전, 설정·데이터 경로, 출처.

숫자는 저장된 원장/결과 파일에서 계산한다. 보기 좋은 보고서를 위해 수치를 수정하지 않는다. 실거래 전환을 자동 실행하지 않는다.
